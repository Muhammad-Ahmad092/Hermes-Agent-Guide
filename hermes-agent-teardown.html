01

What the thing actually is

Hermes is one agent core wrapped in six independent front ends. A single synchronous conversation loop — model call, tool dispatch, repeat — is driven by a prompt_toolkit CLI, an Ink/React TUI, a messaging gateway spanning ~25 chat platforms, an Electron desktop app, a browser dashboard, and an ACP server for editors. None of them reimplements the loop; they all instantiate the same AIAgent.

Capability is deliberately pushed outward. The tree ships 121 tool modules, 199 bundled skills, 36 model-provider plugins, 22 platform plugins, 10 memory backends, and 8 terminal execution backends — yet the tool schema sent on every API call is a hand-curated list in a single file. Two stated invariants explain most of the structure:

Per-conversation prompt caching is sacred. Anything that mutates past context, swaps toolsets, or rebuilds the system prompt mid-conversation invalidates that cache and multiplies the user's cost.

The core is a narrow waist; capability lives at the edges. Every model tool we add is sent on every API call, so the bar for a new core tool is high.

AGENTS.md · "What Hermes Is"

Those aren't aspirational comments — they show up as mechanics. Skill slash-commands are injected as user messages rather than edits to the system prompt. Desktop-only tools (project_*, read_terminal) are excluded from the core bundle and enabled per session by session source, explicitly not by a process environment variable, so a desktop client talking to a remote backend still gets them. Context compression is named in the code as the single sanctioned exception to cache stability.

02

The shape of the system

Six surfaces, one loop. The interesting boundary is the one between the surface and the agent: TypeScript owns pixels, Python owns sessions, tools, and model calls, and they meet over newline-delimited JSON-RPC.

03

Layer by layer

Agent core

The turn loop, provider adapters, context compression, prompt assembly, credential pooling, budget and deadline enforcement. run_conversation was ~3,900 lines inside run_agent.py before being extracted to agent/conversation_loop.py; the original is now a thin forwarder that keeps existing monkeypatches working.

run_agent.py (9,051 lines) · agent/ (140 modules) · agent/conversation_loop.py · agent/context_compressor.py · agent/prompt_builder.py · agent/credential_pool.py

Tool layer

Import-time self-registration: each tools/*.py calls registry.register(), model_tools.py triggers discovery, and toolsets.py decides what reaches the schema. Toolsets are per-platform bundles — browser, kanban, delegation, coding, desktop_ui, and ~30 more — with _HERMES_CORE_TOOLS as the default.

tools/registry.py · model_tools.py · toolsets.py · tools/environments/{local,docker,ssh,modal,daytona,singularity,vercel_sandbox}.py

State

One SQLite database per profile holds sessions, messages, reasoning, and rewind markers, with FTS5 full-text search (plus a native trigram index for CJK). Search, portability, and schema live in sibling modules rather than one file.

hermes_state.py (13,086 lines) · hermes_state_search.py · hermes_state_schema.py · hermes_state_portability.py · native/fts5_cjk/

Surfaces

CLI (cli.py, 20,298 lines) and TUI are peers, not layers — hermes --tui replaces the classic CLI entirely. The dashboard embeds the real TUI through a PTY bridge instead of reimplementing chat in React; the desktop app is the one surface with its own transcript and composer.

cli.py · hermes_cli/ (204 modules) · ui-tui/ (Ink) · tui_gateway/ · apps/desktop/ (1,434 files) · web/ · acp_adapter/ · gateway/

Extension edges

Plugins register tools, hooks, slash commands, dashboard pages, and platform adapters through a PluginContext facade — capability-declared and consent-gated since manifest v2. Skills are Markdown with frontmatter, compatible with the agentskills.io standard.

plugins/{model-providers,platforms,memory,image_gen,kanban,observability}/ · skills/ · optional-skills/ · hermes_cli/plugins.py

Scheduling & queues

Cron drives unattended jobs with a hard 3-minute interrupt, catchup and grace windows, and a cross-process tick lock. Kanban is a durable board where the dispatcher claims tasks and spawns whole profiles as workers, board-isolated by a pinned env var.

cron/{jobs,scheduler,monitor}.py · tools/kanban_tools.py · hermes_cli/kanban.py · plugins/kanban/

04

The learning loop

This is the part that distinguishes Hermes from a tool-calling wrapper: four separate mechanisms that write back into future turns, each with its own store and its own governor.

Memory

10 pluggable providers (Honcho, mem0, supermemory, OpenViking, hindsight, RetainDB, holographic, byterover…) behind one interface, with per-profile isolation. Nudges to persist knowledge were moved out of inline prompt text into a background review pass so they stop invalidating the cache.

agent/memory_manager.py · plugins/memory/

Skills & the curator

199 bundled skills, plus whatever the agent writes for itself. The curator tracks per-skill use/view/patch counts in a sidecar and auto-archives stale ones — but only skills with created_by: agent, never bundled or hub-installed, never deleting, and never touching a pinned skill.

agent/curator.py · tools/skill_usage.py · hermes_cli/curator.py

Session recall

FTS5 search over the agent's own history, exposed as a single session_search tool with discovery, scroll, and browse modes and no LLM in the path. A trigram index replaced the old LIKE fallback so CJK queries actually match.

hermes_state_search.py · native/fts5_cjk/

Background review

After complex turns, an auxiliary model reviews the transcript and proposes memory writes and skill edits, routed to a selectable aux model rather than the main one. Writes pass through an approve/deny gate, and bundled or pinned skills carry protection rules in the review prompt.

agent/background_review.py · agent/auxiliary_client.py

Assessment

Read as a codebase rather than a product: what the structure buys, and where it will hurt.

Holds up well

  • The narrow waist is real, not rhetorical. Desktop tools gated by session source, kanban tools gated by env presence, MCP servers exposed as separate toolsets — the schema stays small while the product grows. Very few codebases enforce a stated invariant this consistently across 1,000 features.
  • Surfaces don't fork the loop. The dashboard embedding the real TUI over a PTY instead of rebuilding chat in React is the right call and is written down as a rule, with an explicit carve-out for sidebars and inspectors.
  • Extension points are load-bearing. 36 providers, 22 platforms, and 10 memory backends live as plugins with capability declarations and consent gating, so the interesting churn happens outside the core.
  • Failure modes are engineered, not hoped for. Cron's 3-minute hard interrupt and tick lock, kanban's failure limit and auto-block, delegation's depth and concurrency caps, a durable delivery-obligation ledger for final responses — these read like scars that were paid for and then fixed properly.
  • 3,130 test files with explicit rules against change-detector tests and against writing to the real ~/.hermes.

Where the strain shows

  • Four files carry too much. cli.py at 20,298 lines, hermes_state.py at 13,086, run_agent.py at 9,051 even after the loop was extracted. The extraction pattern works (conversation_loop.py proves it) but has only been applied to the worst offender.
  • Config surface is enormous. A 101 KB cli-config.yaml.example and a 24 KB .env.example mean feature discovery depends on documentation quality, and a mistyped key fails quietly until a startup validator catches it.
  • Behavior lives in defaults. Because features land compatibly behind flags, the effective agent depends on a long chain of default values — and several PRs exist only to flip one. Reasoning about "what does Hermes do" requires reading config, not just code.
  • Overlapping mechanisms for adjacent jobs. Background delegation, cron, kanban, and terminal(background=True) all run work out of band with different durability guarantees; the docs draw the line explicitly, which is a sign users kept crossing it.
  • Platform breadth is a support surface. ~25 chat platforms, 8 execution backends, and 3 desktop OSes multiply into a test matrix no CI run fully covers — which is consistent with fix work outnumbering features four to one.
